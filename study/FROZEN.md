### 3.1 Batch identifiers

`--batch-id` is a **required** CLI argument with no default
(`harness/cli.py`, `parser.add_argument("--batch-id", required=True)`). Results are written to
`results/<stage>/<batch_id>/<run_id>/` (`CONTRACTS.md` §2), i.e. `results/stage1/<batch_id>/…` in
`harness/cli.py` (`batch_dir = os.path.join(results_root, "stage1", batch_id)`).

The batch id is load-bearing in four places, so it cannot be chosen after dispatch:

1. it names the results directory;
2. it is hashed into every per-run seed and tool-order seed (§3.3);
3. it seeds the within-tranche shuffle that fixes condition order (§3.2);
4. it is written into `tranches.json` and checked on every later invocation — a resume under a
   different batch id is refused (`assert_tranche_manifest_unchanged`: *"the recorded manifest names
   batch {…}, this dispatch is batch {…}"*).

RULED (PM, step 10) — **four distinct batch ids, one per plan**, fixed here because the batch id
enters every per-run and tool-order seed and `tranches.json` binds one plan per batch directory:

| Plan file | Batch id | Config |
|---|---|---|
| `plan_recorded.yaml` | `recorded-core-s1` | `config_recorded.yaml` |
| `plan_family9_recorded.yaml` | `recorded-family9-s1` | `config_recorded.yaml` |
| `plan_fresh_recorded.yaml` | `recorded-fresh-s1` | `config_recorded_partb.yaml` |

### 3.2 Condition order — the exact algorithm

Verbatim from the committed code, in execution order:

1. **Expansion.** `build_cells(plan, scenarios_by_id)` (`harness/cli.py`) walks `plan["cells"]` in
   file order and, for each entry, nests `for condition in entry["conditions"]` → `for model_name in
   entry["models"]` → `for repeat in range(entry.get("repeats", 1))`. The expansion order is
   therefore fully determined by the committed plan file and carries no randomness.
2. **Tranche split.** `build_tranches(cells)` reads the set of repeat indices, takes `final` = the
   largest, and produces at most two tranches: tranche 1 = every cell with `repeat_index < final`
   (label `"repeats {first+1} to {final}, every cell"`); tranche 2 = every cell with
   `repeat_index == final` (label `"repeat {final+1}, every cell"`). A plan with a single repeat
   level is one tranche; an empty tranche is never materialized. This is R39 amendment F5: every
   repeat below the final one dispatches everywhere before any final repeat begins, so a batch that
   stops early is still balanced across conditions and subjects.
3. **Tranche manifest.** Each tranche's manifest is
   `{"tranche": index, "label": label, "repeat_indices": [...], "cells_planned": n,
   "planned_run_ids": sorted(run_ids)}`. The list is written to `tranches.json` in the batch
   directory **once** (`record_tranche_manifest`) and thereafter only verified, never rewritten
   (`assert_tranche_manifest_unchanged`; `TrancheManifestMismatch` on any difference in tranche
   count, repeat indices, or run-id membership). The frozen tranche manifest is also the
   all-attempts denominator for analysis (`PILOT_PROTOCOL.md` §8; disclosure 26).
4. **Ordering gate.** `TrancheDispatcher.assert_ready(index)` refuses to dispatch tranche *n* until
   every tranche with a lower index has completed.
5. **Within-tranche order.** `ordered = list(tranche.cells)` then
   `random.Random(f"{batch_id}#tranche{tranche.index}").shuffle(ordered)`. The seed string is the
   batch id, a literal `#tranche`, and the 1-based tranche index. Nothing else varies it: same batch
   id + same plan ⇒ same dispatch order, on any machine (Python's `random.Random` string seeding is
   deterministic).
6. **Ceiling gate before each tranche.** `meter.assert_tranche_fits(tranche_worst_case_reserved_cost(...))`
   bounds the whole tranche before any cell in it starts (GPT B6). Discretionary checkpoints are
   *not* consulted here; they are evaluated after a completed tranche (§7).

Derived tranche structure of the four committed plans (arithmetic from the committed `expect`
blocks + `build_tranches`; **PM should confirm against the materialized `tranches.json` at

| `plan_recorded.yaml` | 0, 1, 2 | repeats 0+1 = 1,920 cells | repeat 2 = 640 cells |

### 3.3 Run identifiers and seed derivation

All of `harness/ids.py`, verbatim in behaviour:

- `SEED_MODULUS = 2**31 - 1` — "the seed space accepted by the OpenAI seed parameter and by llama.cpp".
- `run_id(batch_id, scenario_id, condition, model_id, repeat_index)` =
  `f"{scenario_id}__{condition}__{safe_model}__r{repeat_index}"` where
  `safe_model = model_id.replace("/", "-").replace(":", "-")`.
  **Note for the record: the run id does not embed the batch id** — batch separation is by
  directory. `_assert_run_ids_unique` enforces uniqueness within a batch directory.
- `_digest(*parts)` = `sha256("\x1f".join(str(part) for part in parts))`, hex.
- `run_seed(batch_id, scenario_id, condition, model_id, repeat_index)` =
  `int(_digest(batch_id, scenario_id, condition, model_id, repeat_index, "seed")[:16], 16) % SEED_MODULUS`.
- `tool_order_seed(...)` = the same digest with the trailing literal `"tool_order"` instead of
  `"seed"`, same truncation and modulus. Kept separate on purpose: *"changing the sampling seed in a
  replication does not silently change the tool order as well (methods 4.10)"*.
- `session_id(run_identifier)` = `"sess-" + _digest(run_identifier, "session")[:16]`
- `instance_id(run_identifier, generation=0)` = `"inst-" + _digest(run_identifier, "instance", generation)[:16]`
- `event_id(run_identifier, sequence)` = `"evt-" + _digest(run_identifier, "event", sequence)[:16]`
- `tool_call_id(run_identifier, turn, index)` = `"call-" + _digest(run_identifier, "call", turn, index)[:12]`
- `task_id(run_identifier, generation=0)` = `"task-" + _digest(run_identifier, "task", generation)[:12]`
- `utc_now()` = RFC 3339 UTC with millisecond precision (`%Y-%m-%dT%H:%M:%S.` + `mmm` + `Z`).

Design rationale as committed: *"Methods 4.6 wants run order randomized and every run reproducible;
a derived seed gives both without a seed file that can drift from the results."* There is **no seed
file**: cell expansion, the tranche split, the dispatch order, the per-run sampling seeds requested and
the tool order all reproduce from the batch id alone. The subject responses do not. Only the local arm
honours a sampling seed — the committed smoke records `supported=False` on all eight API-subject runs
and `supported=True` on the four local ones (`evals/runners/stage1/SMOKE_REPORT.md`) — so a replay
reissues the same requests, not the same completions.

`run.json` records `seed` and `seed_supported` per run alongside `temperature`, `top_p`,
`max_tokens`, `thinking`, `tool_order`, `max_turns`, `max_tool_calls` (`CONTRACTS.md` §2).

### 3.4 Analysis-side seeds

Distinct mechanism, also committed. `evals/grading/analysis.py` and `evals/grading/part_b_analysis.py`
share `stable_seed(*identifiers)`:

```
material = "|".join(sorted(str(value) for value in identifiers))
return int(hashlib.sha256(material.encode()).hexdigest()[:16], 16)
```

— i.e. **sorted** identifiers, `|`-joined, SHA-256, first 64 bits. This is the "seeds from sorted
identifiers" of `PILOT_PROTOCOL.md` §8 and disclosure 10. Applied to:

- scenario-cluster stratified bootstrap: 2,000 resamples, unit = scenario within family
  (`stratified_bootstrap(..., samples=2000)`; `"bootstrap_unit": "scenario within family"`,
  `"wilson_confidence": 0.95`).
- the confirmatory two-sided scenario-cluster sign-flip test: 20,000 draws
  (`sign_flip_p(differences, stable_seed("two-sided", endpoint, *identifiers), 20000)`).
- Part B: `bootstrap_seed = stable_seed(ENDPOINT, denominator, model_id or "pooled", *identifiers)`
  and `sign_seed = stable_seed("two-sided", ENDPOINT, *identifiers)`; both seeds are written into
  the artifact as `bootstrap_seed` / `sign_flip_seed` with `"sign_flip_samples": 20000`.

## 10. SHA-256 manifest and digest

Generator: **`tools/make_manifest.py`** (committed; created at step 7). Behaviour, read from the
tool:

- It hashes **the working tree**, not the git object store. On a dirty tree that would seal dirty
  bytes under a HEAD-shaped name (Grok's step-7 review), so a freeze run **refuses** unless
  `--allow-dirty` is passed — and `--allow-dirty` is documented as *"verification only, never a
  freeze"*.
- File set = `git ls-files`, **sorted**. A tracked path missing from the working tree is a hard
  refusal, not a silent skip.
- Each manifest line is `f"{sha256_hexdigest}  {path}"` (two spaces), joined with `"\n"` and
  terminated with a trailing `"\n"`.
- **The recorded digest is `sha256(manifest_text.encode("utf-8"))`, printed as
  `manifest sha256: <64 hex>`** — the digest of the manifest file itself, not of any tree object.
  This single value is what FROZEN.md records.
- With `--out F` it writes the manifest lines to `F` and additionally prints `wrote F (<n> files)`.
- **Precondition for the freeze run: `MANIFEST.sha256` must not exist on disk when it starts.** The
  clean-tree gate reads `git status --porcelain`, which counts untracked files, and it runs before
  the write — so once an earlier `--out MANIFEST.sha256` run has left the file behind, every later
  invocation refuses, including the one that would overwrite it, and the refusal says *"commit
  first"*, which is the wrong action at that moment. Delete it (`rm MANIFEST.sha256`) and re-run.
- Deterministic: same tree, same manifest, same digest. *"The manifest is committed once, at the
  freeze, by the FROZEN-S1 flow; running the tool at any other time is a verification, not a release
  step."*

RULED (PM, step 10; the timestamp step added 2026-08-26) — the freeze sequence, executed in Grant's
sitting. Every command runs from the repository root, and `$PY` is the project virtualenv's
interpreter (§2.2, §6).

1. **X lands.** The freeze-content commit **X** is committed with a clean tree: everything in this
   document except the fields still marked `AT-TAG` — of which four are filled by steps 3 and 4
   below (X's own SHA, the manifest file count, the manifest digest, and the freeze date).

2. **The manifest is built at X.**

   ```
   rm -f MANIFEST.sha256          # the tool refuses if it is already on disk (see above)
   $PY tools/make_manifest.py --out MANIFEST.sha256
   ```

   It prints `wrote MANIFEST.sha256 (<n> files)` and `manifest sha256: <64 hex>`. Both numbers are
   recorded now, straight off the terminal.

3. **The three knowable at-tag values are written into the working tree before Y exists.** X's full
   SHA (`git rev-parse HEAD`) into §1; the file count and the digest from step 2 into §10's table.
   None of the three is circular: X is committed before Y is written, and the manifest is computed
   at X.

4. **The freeze timestamp T is chosen, not read back afterwards.** Read the clock once, at the top
   of this step:

   ```
   T=$(date -u +%Y-%m-%dT%H:%M:%S+00:00)
   echo "$T"
   ```

   That value is **T** for the rest of the sitting. Write it verbatim into §1's *Freeze date (UTC)*
   row here, and into the matching freeze-date field of `docs/OSF_REGISTRATION.md`. T is the real
   wall-clock moment of the freeze, taken a few minutes ahead of the commit — it is fixed in
   advance, never invented.

5. **Y is committed with T as both of its dates.**

   ```
   git add MANIFEST.sha256 FROZEN.md docs/OSF_REGISTRATION.md
   # plus any other document whose at-tag fields this sitting filled
   GIT_AUTHOR_DATE="$T" GIT_COMMITTER_DATE="$T" \
     git commit -m "FROZEN-S1: manifest and final freeze document"
   ```

   Y is the child of X and carries `MANIFEST.sha256` and the final `FROZEN.md`. No amend, no second
   commit: the date in the document is true of the commit that contains it, on the first write.

6. **Read-back check, before the tag.**

   ```
   TZ=UTC git show -s --format=%cd --date=iso-strict-local HEAD
   ```

   must print T character for character, exactly as §1 now records it; `--format=%ad` prints the
   same value because step 5 set both variables. Use this form and not `%cI`: because T carries the
   `+00:00` offset, git stores that offset and `%cI` happens to agree here, but the `TZ=UTC` form is
   the one that is right whatever offset a commit stores. If the two disagree — a typo in T, a shell
   that dropped the variable — correct the row and redo Y (`git commit --amend --date="$T"` with
   the same two variables set — `--amend` on its own reuses the original commit's author date
   whatever `GIT_AUTHOR_DATE` says, so the `--date` is not optional here — or reset and recommit).
   Nothing anywhere records Y's own SHA, so Y may be rewritten freely right up to the tag; X, the
   manifest and the digest are untouched by that.

7. **Grant tags Y and pushes.** `git tag FROZEN-S1` in his own hand, then the branch and the tag:
   `git push --force-with-lease origin master`, then `git push origin FROZEN-S1`. The branch push
   replaces published history rather than extending it — the email-identity repair rewrote commits
   that had already been pushed, so every commit from the first repaired one onward carries a new
   SHA. That replacement is deliberate and owner-approved (private repository, single clone), the
   identity rewrite moved commit metadata rather than content, and the pre-repair chains are kept at
   `backup-pre-email-fix` and `backup-pre-audit-pass`.

WHY the timestamp is chosen rather than discovered (PM, 2026-08-26, found while building the
freeze-sitting sheet): §1's freeze-date row is written *inside* Y and describes Y, so a session that
reads the value back after committing can only honour it by amending or by adding a second commit —
and either makes the tagged bytes differ from the bytes that were checked. Setting `GIT_AUTHOR_DATE`
and `GIT_COMMITTER_DATE` to a T chosen a few minutes earlier removes that circularity rather than
hiding it. The alternative was to leave the row as a read-back instruction carrying no literal date:
honest, but it leaves this registration's own rule — nothing is submitted while any at-tag marker
remains, save the OSF identifier and submission timestamp — unsatisfiable for that one field, and
the OSF form needs a literal date regardless. The other three at-tag values needed no such
treatment: X's SHA and the manifest's digest and file count all exist before Y is written.

By construction the digest covers the full tree at X; the only content outside its own digest is
`MANIFEST.sha256` and the at-tag values Y writes into this document, into
`docs/OSF_REGISTRATION.md`, and into `FREEZE_CHECKLIST.md` (the §E/§F tick fills), and this
paragraph is the written record of that exclusion.

It follows that re-running `tools/make_manifest.py` **at the tag** does not reproduce the recorded
digest, and is not meant to: the tree at Y carries one tracked file the tree at X did not
(`MANIFEST.sha256`) plus those at-tag fills in two already-tracked documents, so the file count is
one higher and the digest differs. Two checks do work, and they are the ones to run. First,
`sha256sum MANIFEST.sha256` at the
tag must equal the digest recorded in the table above — the recorded value is the digest of the
manifest file itself, so this verifies the manifest has not been altered since the freeze. Second,
regenerating from a clean checkout of `FROZEN-S1^` — the content commit X, named by that ref rather
than by a hand-copied SHA — must reproduce both the file count and the digest exactly.

### 10.1 Dispatching the recorded run from a separate checkout

RULED (PM, 2026-08-26): the harness writes a `cost.jsonl` beside every run under
